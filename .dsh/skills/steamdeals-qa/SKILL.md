# 质检（SteamDeals / gameprice）

> **夜班身份（2026-11-19 起）**：若本会话是夜班监工派出的工人（或监工自己）在做质检，先读
> `steamdeals-nightshift` 技能（工人只提交代码/测试/QA 报告，不改发布文档）。

> **开工前自检（2026-11-18 修订：允许复用会话，不再强制新开会话）**：动手/回复实质内容前先自检：
> 1. 交接消息是否满足 `docs/HANDOVER.md` §7 的**自包含 8 项**（仓库与 HEAD、技能、编号、规格路径、范围、验收、纪律、汇报格式）——不完整先补全，不得凭记忆开工；
> 2. 本会话是否残留**别的编号的未完成任务**（未提交改动、写到一半的报告）——有则先收尾旧任务或说明归属，不把多个编号的工作混进同一批提交；
> 3. 目标编号是否已被其他会话占用（TODO 状态 / 未提交改动 / 对话声明）——占用就跳过并等待（HANDOVER §10.5）。
>

> **路径基准**：下文 `docs/…`、`src/…`、`frontend/…`、`test/…` 都相对**仓库根** `F:\dsh\gameprice`，
> 不是本 SKILL.md 所在目录。开场先 `git rev-parse --show-toplevel` 确认在仓库根。
>
> **技能维护**：本文件随仓库提交；改动后执行 `pwsh F:\dsh\gameprice-skills\sync.ps1` 同步镜像仓库
> （junction 与「不维护第二份副本」的完整说明见 `steamdeals-requirements` SKILL.md 头部）。
>
> **分工**：`steamdeals-requirements` 出需求与开发描述 → `steamdeals-dev` 实现并验证 →
> **`steamdeals-qa` 验收核对**。结论只有三档：✅ 放行 / ⚠️ 有条件放行 / ❌ 打回。

## 0. 边界：只判不改

| 做 | 不做 |
|---|---|
| 读需求、拆条目、列检查计划、git/代码取证 | 写业务代码、改需求文档、改测试、改文档 |
| 亲自重跑验证命令（§3 第 6 步） | `git add/commit/tag/push`、发版、触发构建 |
| 写 `docs/QA-<TOPIC>.md` + 对话给结论 | 碰服务器、连生产库（硬规则 4） |
| 打回复检（§8），多轮留痕 | 替开发"顺手修"任何东西 |

- QA 报告 `docs/QA-<TOPIC>.md` **默认不提交**（所有者要求存档时才提交）。
- 引用不重复：验证命令以 `steamdeals-dev` §7 为准；"没跑过不许说做完"引用 `verify-before-done`。
- 若同会话质检出现放水（放行后仍有漏功能），改用**独立裁判**：新开会话，只传规格路径 + 基线/HEAD 哈希，
  不带开发会话的任何结论。

## 1. 触发与适用

- **开工前登记（2026-11-19 起，防并发抢占）**：读 [docs/ACTIVE-SESSIONS.md](../../../docs/ACTIVE-SESSIONS.md)，
  登记本会话（条目 / 会写的文件：QA 报告、可能回写的 TODO 状态行）；若需跑 e2e 全量/模拟器/报告，
  同样受「独占资源」令牌约束（见 `steamdeals-test` §6.0）。收工注销自己那行。
- `steamdeals-dev` 在「提交推 main」之后**必须**调用本技能；❌ 打回项补齐并复检通过，才算交付。
- **何时用**：开发完成后初检、打回复检后。
- **何时不用**：需求讨论阶段（那是 `steamdeals-requirements` 的事，质检不参与方案取舍）。
- **输入来自待办清单（2026-11-06 所有者要求）**：开发者说"做完了"时必须给出 **TODO 编号**；
  质检按该编号在 [docs/TODO.md](../../../docs/TODO.md) 找到条目与规格，不接受"你去看我提交"这种转述。
- **检查完必须回写状态**：把该条目从 `待质检` 改成 `质检通过` 或 `质检打回`（打回时在条目里写一句打回摘要），
  并在 `docs/REQUIREMENTS-INDEX.md` 同步；**质检不写 `已发布`**（那是发版后的事）。`质检通过` 条目**仍留在
  [TODO.md](TODO.md)**（等构建）；发布后由 `steamdeals-build` 把它移入 [DONE.md](DONE.md)。
  回写即可——README 不再有「开发进度」生成块（2026-11-12 起下线，没有 `todo:progress` 命令与 `docs-progress` 门禁）。
- **并发写 TODO/INDEX/DONE**：回写状态前按 [HANDOVER.md](HANDOVER.md) §10.1 探测占用（含 `docs/.ledger-lock` 清单锁）；
  被占用就跳过状态回写，照常完成判定、报告与结论（注明「状态回写待补」），由收尾复盘按 §10.3 补回。
  回写提交用会话隔离脚本（写前 `node scripts/commit-own.mjs lock <编号>`、写完 `unlock`）：
  `node scripts/commit-own.mjs <编号> "docs(qa): …" -- docs/TODO.md docs/REQUIREMENTS-INDEX.md`。
- **开工前查重，不重复质检（2026-11-18 所有者新规）**：动手前先确认该编号**是否已被其他会话质检**——
  命中任一即视为"他人进行中"：① TODO 状态已是 `待质检 / 质检通过 / 质检打回`；② `docs/QA-<编号>.md`
  已存在且最近被修改或已提交；③ 对话里已有别的会话声明在做该编号的质检。
  **认定为他人进行中 → 跳过并等待，不重复质检、不重跑验证、不重写报告**；只做只读确认（看报告/看状态），
  汇报里写「跳过 <编号>：已由其他会话质检（依据：QA 报告 / 提交 / 状态），等待其结果」。

## 2. 输入：判据与证据，都不信转述

1. **判据**：docs 规格文档「验收」章节的编号清单 + 开发描述（requirements §6）的【范围】【验收】【红线】。
   判定以**规格验收为唯一判据**，开发描述只当背景。
2. **版本核对**：开工先 `git log --oneline -5 -- docs/` 确认规格没在开发期间被改；不一致先提示，
   以最新 HEAD 的规格为准。
3. **范围**：开发描述【范围】的"做/不做"（分批交付只判本期）；没有范围声明就默认规格全量。
4. **基线**：开发描述【背景】里的 HEAD 短哈希 = 基线；证据范围 `git diff <基线>..HEAD`。
5. **git 取证**（不信开发转述"我做了、全绿了"）：
   ```powershell
   cd F:\dsh\gameprice
   git status --short
   git log --oneline -5
   git diff --stat <基线>..HEAD
   git diff <基线>..HEAD
   git tag --list
   ```
6. **条目判定以最终仓库状态为准**：diff 只用来定位改动与"查多"；某条目由基线前已有代码满足也算 ✅
   （注明证据来源），不能因为"不是本次 diff 做的"就误判缺失。

## 3. 七步流程

0. **对序号**：确认开发者给的 TODO 编号存在、且状态是 `待质检`/`已实现待发版`；否则先要编号再开工。
   再看条目的 `依赖：`——前置还没到 `质检通过`/`已发布` 时判"暂缓检查"并说明，不要硬判 ❌。

1. **拆条目**：规格「验收」逐条 + 纪律项 → 可判定条目表（编号、要求、可观测点）。
2. **列检查计划**：每条写检查手段——grep 什么、读哪个文件、跑什么命令。先透明，后动手。
3. **双层核对**：规格 → 开发描述改动清单（清单本身漏了条目 = 开发漏）；再清单 → 代码。
4. **逐条取证**：
   - 每条到代码找证据，证据格式 `文件:行号 + 关键片段`；
   - **四方一致**：后端接口 / 前端消费 / 测试断言 / 文档描述，同一条目四处联动缺一即漏；
   - **测试"真锁住"**：判据与反向自检方法见 `steamdeals-test` §3（断言质量三原则）与 §10（反模式清单）；"测试全绿" ≠ "测试覆盖了本条目"。
5. **查多**：diff 全量过目；需求外改动单列「风险提醒」，不直接判错。
6. **亲自重跑验证**（命令以 `steamdeals-dev` §7 为准，**不重复贴命令**；QA 侧仅以下差异）：
   - 主链全量 `npm test` **默认不跑**（开发刚跑过 + CI 每推必跑）；只在触及共享底层 / 断言存疑 / 打回复检兜底时跑（主链已分段 `test:1~test:4`，兜底只跑失败段）；
   - e2e 全量**默认不跑**（发版后由独立报告会话执行，见 `steamdeals-test` §2.3）；QA 轮只跑本批相关矩阵行（`npm run e2e -- --only=<本批功能>`）；
   - 纯文档/注释/文案改动可降级为抽查（grep 关键片段，并写明"本改动无自动化测试可跑"）。
   **验证失败 = 直接打回，质检不修。**
7. **出报告**：写 `docs/QA-<TOPIC>.md`（§5 格式，**必须含「功能清单」表**）+ 对话里给头部三行结论与同一张功能清单（§9 格式）。

## 4. 判定标准

| 判定 | 含义 |
|---|---|
| ✅ 通过 | 代码证据支持，功能行为满足需求 |
| ❌ 缺失 | 仓库里找不到实现（含"改动清单列了但代码没做"） |
| ⚠️ 偏差 | 有实现但行为不符（文案错、位置错、口径错、范围不符） |
| 🔎 需人工确认 | 本地/静态无法验证（页面目视、真实 Steam 数据、部署后效果） |
| 📋 需求缺陷 | 验收标准歧义/矛盾/不可验证 → 打回需求方，不算开发问题 |

- **行为满足即通过**，实现方式自由（提示用 el-alert 还是 `<p>` 都行）；只有行为不符才判 ⚠️，防机械假打回。
- **无法验证绝不硬判**：宁写 🔎 也不猜 ✅/❌——质检的信用靠这条，防质检自己假通过。
- **页面类条目必须核对 demo（2026-11-17 起）**：规格附 `docs/design/*.html` 时，打开 demo（或同名 `.png`）
  与实现截图逐项对比（层级 / 状态 / 间距 / 移动端 / 文案）；**有 demo 却不一致 → 判 ⚠️ 偏差**；
  规格要求了 demo 却没有 → 打回需求方（📋 需求缺陷）。
- **视觉核对（2026-11-23 起，模型不支持读图时）**：`read_image` 报 `does not declare image input` 时，
  ① 先看开发侧 DOM 断言证据（关键元素/Tab 状态/按钮 class）；② 需要看图时用
  `subagent(provider="deepseek-official", model="deepseek-flash", prompt="读取图片 <绝对路径>，输出结构化描述：
  ①区块与文字 ②按钮样式 ③布局问题 ④Tab 状态；只读图不改代码")`；
  ③ 或把截图路径交所有者/lead 人工确认——**不许不看图就判 ✅**，也不许猜。

- **执行要求（2026-11-25）**：② 前先 `list_subagent_models(provider="deepseek-official")`；`deepseek-flash` 存在则**必须用**；
  只有查不到/调用失败才走 ③，并在 QA 报告写明「已查路由，flash 不可用：<原因>」。

- **功能清单是必出项（2026-11-06 所有者要求）**：把本编号（或本批多个编号）交付的**所有用户能感知的功能**
  逐条列出来——不是抄规格验收条目，也不是列"改了哪些文件"；所有者靠这张表判断"这个功能到底有没有"。
- 一条功能一行：规格 §验收 的每条可观测能力都落到一行，**不许合并、不许抽样**；多编号时加编号列，全部列出。
- 状态四档：`✅ 已交付` / `⚠️ 偏差` / `❌ 缺失` / `🔎 待人工确认`，与「逐条核对」的判定一致。
- 「入口」写清用户从哪点进去（页面 → 按钮 / 接口路径），让所有者能自己复验。
- 表里每个 `⚠️`/`❌` 必须能在「打回清单」按编号找到对应项。
- 这张表要**同时出现在报告和对话汇报里**（§9）：报告存档，对话给所有者看。
- 头部三行结论，所有者 10 秒看懂。
- 打回清单严重度：漏验收 = 必修；偏差 = 必修或说明；风险 = 记录即可。
- QA 文档默认**不进 git**；相对链接必须指向真实文件（`test/docs.test.js` 会校验 docs 断链）。

## 6. 纪律固定检查项（每条都查，对应 steamdeals-dev §0/§8 硬规则）

1. `git tag --list`：无擅自新增 tag（硬规则 5，打 tag = 触发构建）；
2. diff 是否碰部署/服务器配置（compose 文件、DEPLOY 相关、凭据）；
3. 构建产物（`frontend/dist/`、`*.log`、`data/*-pgdata/`、`out/`、`logs/`）是否进了提交；
4. 是否按要求推 `main`（开发描述【红线】要求）；
5. 文档收尾：`docs/PROJECT-OVERVIEW.md` 是否同步（steamdeals-dev §6 必改项，"代码新、文档旧"即漏）。

## 7. 典型漏项清单（优先按此排查；发现新漏项模式就追加，skill 越用越准）

> 与 `steamdeals-test` §10（反模式清单）重叠的三条不在此重复：**测试没锁住新行为**（test §10 #1/#4）、
> **新测试没进主链/矩阵**（test §10 #9）、**真机条目未标注就判 ✅**（test §10 #10）——以 test §10 为准。

1. 后端删/改字段，前端没同步（接口返回体改了、调用方没跟上）
2. 文档未同步（PROJECT-OVERVIEW / README / CHANGELOG / 规格状态词）
3. 开发描述改动清单本身漏了规格条目（双层核对第一层）
4. 顺手改了需求外代码（scope creep）
5. Element Plus 新组件没注册 → 页面**静默**不渲染
6. 日志事件没按 `域.动作`，失败路径没带原因
7. 状态词写错（把"待开发"写成"已发布"）

## 8. 复检（第 N 轮）

- 只重查：打回项 + 新增 diff + `npm test` 兜底（防"修 A 弄坏 B"）；不每次全量重来。
- 每轮在报告「复检记录」留痕，直到 ✅ 放行。
- 开发对判定不服 → 写进「争议项」（申辩 + 质检意见并列），质检不私了，所有者裁定。

## 10. 收尾自检（每次结束前逐条过）

1. 每条判定都有证据（文件:行 + 片段）？没有证据的判定不算数。
2. 🔎 项诚实列出了吗？有没有硬判 ✅/❌？
3. 重跑验证的命令与关键输出贴了吗？
4. 报告落 `docs/QA-*.md` 且未提交了吗？
