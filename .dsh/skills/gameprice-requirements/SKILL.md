## 0. 边界：这是聊需求，不是开发

**只做**：澄清目标 → 核对代码现状 → 方案取舍 → 定义验收 → 写规格文档 → 更新待办留痕 →
**产出开发描述（§6，必须）** → 交给开发会话。

**不做**（被要求也不做，说明原因并给开发描述）：

- 不改 `src/` `frontend/` `web/` `test/` `scripts/` 里的任何业务代码或测试；
- 不跑 
pm test` / 
pm run frontend:build` / 任何 `sync` `backfill` `heat` 采集命令，不连生产库；
- 不 `git add/commit/tag/push`，不写 CHANGELOG 版本条目，不承诺版本号或上线时间；
- **不碰服务器（硬规则 4），不触发构建**（硬规则 5：只有所有者明确说"构建 vX.Y.Z"才能打 tag）。
- **给不给服务器命令，按阶段分**（2026-11-05 所有者确认）：
  - **需求/设计阶段**：不给"请你去服务器执行"的命令。需要线上事实时按顺序退让：① 后台页面能不能看到
    （运行日志 / 访问记录 / 设备与黑名单 / 指标卡）→ ② 确实只能命令行的，写进规格的「部署侧验证」章节；
  - **排查/诊断阶段**（用户在报故障、已经在查问题，或明确要命令）：**可以直接给只读诊断命令**，
    但要满足 §9 的规范（可复制、只读、带判读）；破坏性/写操作一律先问。

**允许写的文件**：`docs/` 下新增或修订的需求/规格文档，以及 `docs/TODO.md`、`docs/ROADMAP.md` 的条目。
**不写** `README.md`、`docs/PROJECT-OVERVIEW.md` 的功能状态——那是"已实现"的对外描述，由开发阶段在交付时同步（否则会把计划写成已完成）。

用户说"顺便改一下"时：按 [CONTRIBUTING.md](../../../CONTRIBUTING.md) 的会话分工（需求讨论 Flash / 实现 Pro）说明这属于开发阶段，产出第 6 节的开发描述即可。

## 2. 现状核对：先有证据，再下结论

需求里每一句"现在没有 / 现在有问题"，都要用 `grep`/`read` 找到代码或文档证据；找不到就写"待核实（谁去核实、怎么核实）"。

**四态口径，不许混说**：代码存在 ／ 有测试覆盖 ／ 本地或真实环境跑通 ／ 未验证（缺凭据、缺网络、缺服务器）。

**容易重复提的需求（已经做了）**：价格历史与史低、多区服并排对比（不折算）、关注与到价提醒（webhook/企业微信/邮件）、采集熔断、封面图缓存、亮暗主题、移动端布局、站点通知中心、设备指纹与封禁、申诉（目前 mailto 流程）、后台十个模块、Steam 多账号绑定与愿望单同步、热度排序与发行时间筛选、访问记录与 IP 黑名单。

**明确不做（撞上就直说理由并给替代方案）**：C2C 最低价进主榜、站内下单/代购、"保证正品"承诺、SteamPy 接入、Fanatical 接入、不同币种折算（会算错，只并排展示）。原文见 `README.md` 的「它明确不做什么」与「已知限制」。

## 3. 澄清清单：一次只问关键的 3–6 个

- **场景**：谁、在什么情况下用、现在怎么绕过、痛在哪一步（要具体动作，不要抽象诉求）
- **范围**：必须做 / 可以后置 / 这次明确不做
- **口径**：金额是整数分；区服与币种是否混算；C2C 参与不参与；历史数据能不能补（价格历史补不回来）
- **权限与安全**：谁能看、谁能改；是否涉及封禁/限流/审计；是否涉及密钥（只记变量名，不记值）
- **自动化（硬约束）**：任何涉及**数据同步/采集/回填/判定**的需求，一律设计成**定时任务**（并入 `jobsFromEnv`），
  不允许"上线后手工跑一遍"，也不允许只给一个 CLI 命令；并且**先问"能不能并进已有任务"**——
  同一个外部响应里已经有需要的字段，就合并（见 §4.1），合并能省掉成倍的请求配额。
- **兼容**：老库升级（`src/store/pg.js` 的 `alter table ... add column if not exists`）、存量回填、没有前端构建产物时的 `web/` 回退页
- **验收**：怎么证明做完了（页面现象 / 接口返回 / 日志事件 / 测试断言），要可观测

需求含糊时**先问再写**，不要用"大概是……"填满文档；不确定的点单列「待确认问题」，编号留给所有者回答。

## 4. 方案取舍必须过的项目约束

逐条对照，撞线就把冲突写进文档，不要偷偷绕过：

| 约束 | 检查点 | 典型踩法 |
|---|---|---|
| 只收官方渠道 | 任何价格/榜单/史低功能都要回答"会不会把 C2C 算进来" | 主榜有两条路径：视图 `v_lowest_official` **和** `daily_prices` 聚合，历史上 C2C 从第二条泄漏成史低 |
| 币种不折算 | 跨区只并排、同币种才比大小 | 顺手加"折合人民币"会让比较结果错 |
| 依赖极少 | 运行时只有 `pg`、`undici`、`@electric-sql/pglite` | 引框架/ORM/SMTP 库要单独论证 |
| PG 15 语法上限 | 禁 `any_value`(16+)、`json_table`(17+) | 本地新库能跑，生产挂 |
| 金额整数分、DATE 当字符串 | 不出现浮点金额；日期统一 `::text` | `pg` 把 `date` 解析成 Date 会差一天 |
| 业务设置走 `src/settings.js` 的 `def()` | 能用页面改的不要塞 env；优先级 DB > env > 默认，热加载约 15 秒 | 新增部署期参数才留在 env |
| 新数据任务必须进调度器 | `jobsFromEnv` + `test/scheduler.test.js` 断言默认参数与开关 | 只加 CLI 命令 = 功能没做完 |
| **数据同步一律定时 + 合并优先** | 先查现有任务能不能顺带做（§4.1）；不能合并才新建，且必须写清单次时长与配额影响 | 新建一个和 `backfill` 请求形态相同的任务，白烧一倍配额 |
| 前端用 Element Plus | 组件**必须注册**（`frontend/src/main.js`），否则页面静默不渲染 | ElDrawer / ElBadge / ElCheckbox 都踩过 |
| 移动端 | `main.css` 断点 1024/768/420 + `mobile-layout` 兜底（「桌面版网站」模式），触摸 ≥44px | 只靠 CSS 压缩 PC 结构 |
| 日志 | 事件名 `域.动作`（`http`/`db`/`adapter.*`/`ingest`/`sync`/`scheduler`/`diagnose`/`process`），失败带原因 | 只写 "failed" |
| 服务器与发版 | 开发侧到"提交 + 打 tag"为止，服务器由部署人员操作，构建等人工指令 | 自行打 tag 触发 CI |

### 4.1 定时任务：先合并，再新建

**判据只有一条**：目标数据能不能从**已有的同一次外部请求**里顺手拿到。
能 → 合并；不能 → 才新建任务，并在规格里写清"为什么不能合并"。

现有 19 个任务（`src/scheduler.js` 的 `jobsFromEnv`）与可合并性：

| 任务 | 请求形态 | 响应里已有 | 可合并给谁 |
|---|---|---|---|
| `backfill` | GetItems 批量 + 逐条 appdetails 回退 | 元数据、价格、**分级字段** | ✅ 状态/分级可并入 |
| `steam-status` | 逐条**全量** appdetails | 价格、分级、`coming_soon` | ✅ 反向也可（已是状态/分级的主供给） |
| `steam-prices` | 批量 appdetails `filters=price_overview` | 只有价格 | ❌ 改逐条会慢 30 倍 |
| `heat` | 逐条 appdetails `filters=recommendations` | 只有评测数 | ❌ 拿不到价格/分级 |
| `catalog` / `rename` | 目录与改名接口 | 名字、appid | ❌ 与价格/分级无关 |
| `steam-accounts` / `steam-claim` | Steam Web API（账号、库、愿望单） | 账号数据 | ❌ 另一套接口 |
| `sonkwo` / `itad` / `gog` / `humble` / `discover` | 各平台自己的接口 | 各自报价 | ❌ 不同来源 |
| `prune` / `backup` / `logs` / `alerts` / `images` / `report` | 本地运维 | — | ❌ 与本议题无关 |

**新建任务的规格必须写这四项**（缺一项视为没设计完）：

1. **合并评估**：为什么不并进 `backfill` / `steam-status` 等已有任务；
2. **单轮时长**：候选条数 ÷ 每小时请求数（Steam 配额 200 次/5 分钟 ≈ 2400 次/小时）；
3. **单轮时长会不会挤占其它任务**：超过几小时就要调小 `*_LIMIT` 分天跑，而不是让一轮挂几天；
4. **续跑游标**：中断后靠哪个字段继续（如 `steam_checked_at`），失败条目要不要写游标。

> 实测教训（2026-11-04）：`steam-status` 默认 `LIMIT=200000`，候选 17.5 万、单轮 73–80 小时，
> 会把 heat/backfill 往后压。规格里必须提前算这笔账。

## 5. 产出物：规格文档（聊完的标准）

**位置与命名**（三者选一，别乱放）：

- 成体系的新功能/改造 → `docs/<TOPIC>.md`（如 `APPEAL-SYSTEM.md`、`MAIL-CONFIG-PAGE.md`、`ADMIN-PARITY.md`）
- 按日期批次 → `docs/<TOPIC>-YYYY-MM-DD.md`（如 `UX-BATCH-2026-11-03.md`）
- 还没排期的探索话题 → 追加到 `docs/ROADMAP.md`（背景 / 现状 / 目标 / 建议落点 / 待确认）
- 已确认要做的 → 在 `docs/TODO.md` 加条目（表格或编号小节）并链接规格文档

**模板**（照 `docs/APPEAL-SYSTEM.md` 的结构，可裁剪，顺序别乱）：

```
# <主题>（待开发）
> 状态：**需求与方案已确认（YYYY-MM-DD），待开发**。
> 关联：[相关文档](相对路径)

## 1. 已确认的决策        ← 表格：# | 决策（只写所有者确认过的）
## 2. 数据模型            ← SQL 草案 / 新增表列；标注迁移方式
## 3. 服务端              ← 接口、鉴权、校验、限流、日志事件
## 4. 前端 / 后台          ← 页面文件落点、交互、空态与移动端
## 5. 设置与配置            ← settings key、默认值、是否热加载
## 6. 调度与自动化          ← 新建任务还是合并到 X（给理由）、间隔、单轮时长、续跑游标、幂等
## 7. 安全                ← 放行规则、字段长度、防刷、密钥
## 8. 验收                ← 可观测的编号清单 + 通用验证（npm test / frontend:build / npm run scan）
## 9. 实施顺序            ← 依赖关系，先修阻塞项
## 10. 待确认问题          ← 编号，等所有者回答
```

**规格文档头部的状态词**：`待讨论` / `已确认待开发` / `开发中` / `已实现并发布`。需求阶段只允许写前两个，
禁止把"建议"写成"已决定"。

> 注意：**规格文档的状态词**与 **`docs/TODO.md` 条目的状态词**是两套——TODO 用
> `待开发 / 依赖阻塞 / 开发中 / 已实现待发版 / 待质检 / 质检通过 / 质检打回 / 已发布 vX.Y.Z / 待排查 / 待决策 / 已过时`。
> 写 TODO 条目时用后者，别混。

文档内链接一律相对路径（`docs/xxx.md`、`../src/xxx.js`）；`test/docs.test.js` 会校验固定文档清单的断链。

## 6. 开发描述（需求确认后**必须**产出，但只写三样）

**硬规则（2026-11-06 所有者要求）**：需求一旦确认，本轮回复**必须**附开发描述，没有它不算聊完。
但开发描述**不再复制长模板**——项目的排期与状态都以 `docs/TODO.md` 为唯一来源，
开发会话读 [docs/HANDOVER.md](../../../docs/HANDOVER.md) 就知道完整流程。

开发描述只写三样：

```
【要做的条目】docs/TODO.md 的 <编号>（状态改为：待开发）
【规格】docs/<文件>.md（§ 关键节号）
【验收要点】<3–5 条，与规格 §验收 一致，供 gameprice-qa 判>
```

配套动作（顺序固定，缺一个都算没落实）：

1. **在 `docs/TODO.md` 建条目**：编号取下一个未用字母，标题写清楚，正文第一行必须是
   `**状态：待开发**`，并链接规格；**紧接着写 `**依赖：**` 与 `**解锁：**` 两行**（无则写"无"）——
   前置未完成时状态用 `依赖阻塞`，不要用 `待开发`；把"待确认/已确认"的事实写进条目，不要只留在对话里；
2. **在 `docs/REQUIREMENTS-INDEX.md` 加一行**：编号 / 主题 / 规格 / 状态 / 是否有开发描述；
3. **本轮回复给开发描述**（上面三行）；
4. 若需求里有真机/线上证据，写进 TODO 条目或规格（开发本机可能复现不了）。
5. **改完 TODO / INDEX 后运行 `npm run todo:progress`**，保持 README「开发进度」块与 TODO 一致（CI `docs-progress` 会校验，规则见 [docs/TODO-PROGRESS.md](../../../docs/TODO-PROGRESS.md)）。

**并发写 TODO（2026-11-06 所有者要求）**：建条目 / 加 INDEX 行之前先确认没有别的会话在写这两份文件
（`git status --short docs/TODO.md docs/REQUIREMENTS-INDEX.md`、`LastWriteTime` 2 分钟内被改过、`.git/index.lock`）；
**发现被占用立即停手**——不改 TODO / INDEX、不提交，把"想加/改什么条目、证据、疑似占用方"报给所有者，
**由人工决定**怎么处理；所有者确认可写后再重读全文、用 `edit` 定点替换。完整规则见
[docs/HANDOVER.md](../../../docs/HANDOVER.md) §10。

> 不要在主对话里当"唯一的传话人"：对话会丢，TODO 不会。任何"以后要做"的结论，
> 只要没进 TODO，就等于没记。

**交给开发会话时只发一句指路**（模板见 [docs/HANDOVER.md](../../../docs/HANDOVER.md) §7）：

```
新需求已入待办：docs/TODO.md 的 <编号>（状态：待开发）。先读 docs/HANDOVER.md → 该条目 → 规格；
做完改状态为「已实现待发版」，调 gameprice-qa，按 HANDOVER §3 汇报「已做/未做/状态更新」。
```

**不要把规格正文、验收清单、代码落点再贴一遍**——TODO 与规格里已有，复制只会造成两处分叉。

## 7. 收尾自检（每次结束前逐条过）

1. 每条结论都有代码/文档依据？没依据的标"待核实"，不写成事实。
2. 决策是否区分了"所有者已确认"与"我的建议"？
3. 有没有偷偷承诺版本号、上线时间、构建？——删掉。
4. 本次是否确实没改任何业务代码、没跑构建、没提交？（回复里明确写这一句）
5. **是否已在 `docs/TODO.md` 建/更新条目**（正文第一行有 `**状态：…**`），并在 `docs/REQUIREMENTS-INDEX.md` 加了一行？
6. **是否已产出开发描述**（§6 三行：要做的条目 / 规格 / 验收要点）？
7. **有没有写清依赖关系**：新条目有 `**依赖：**` / `**解锁：**` 两行吗？前置未完成时状态是 `依赖阻塞` 吗？
   有没有哪些"后续需求必须等这条做完才能定位"的情况没写出来？（例：先加日志，下一条才能诊断）
8. **涉及数据同步的，是否已经设计成定时任务，并写清了"能不能并进已有任务"的理由与单轮时长？**
9. **命令是否符合阶段规则**：需求/设计阶段不该出现"你去服务器执行"的字样；排查阶段允许只读命令，
   但必须按 §9 写清"看什么 / 怎么判读 / 预期值"。

## 8. 本项目踩过的坑（需求阶段就要预判）

- 主榜过滤有两条路径，只堵视图会从 `daily_prices` 漏 C2C。
- Element Plus 组件没注册 → 页面**静默**不渲染，改动清单里要写"补注册 + 防回归测试"。
- `??` 遇空字符串不回退（申诉邮箱就因为水合成 `''` 断了四级回退链）。
- ES module 提升让 `mount` 前的 `router.replace` 无效（封禁页跳转踩过）。
- 杉果页面没有 Steam appid，跨平台只能名称匹配（bigram Dice + 人工确认），匹配率取决于游戏库覆盖。
- Steam 国内直连不可达（需 `STEAM_PROXY`）；`appdetails` 多 appid 批量**只接受** `filters=price_overview`；配额 200 次/5 分钟，价格/目录/回填/热度共用，任务要互斥。
- 本机无 Docker、无 Steam 出口：本地跑不通 ≠ 代码错，需求验收里要写清"哪一步必须在线上验证"。
- **免费/未发售的游戏永远不会有价格**：任何"待同步率"指标都必须先拆出 `free` / `coming_soon`，否则永远归不了零
  （2026-11-04 实测：9.2 万待同步里 25% 是免费游戏，大头是未发售，真正失败的很少）。
- **"零日志"要先怀疑日志开关**：生产 nginx 的 server 块里可能是 `access_log off;`，应用侧也有日志级别过滤；
  在报"请求没生效"之前先确认观测手段开着。
- **接口形态决定可合并性**：批量接口（30 个 appid/请求）与逐条接口（全量 appdetails）能拿到的字段完全不同，
  别假设"反正都是 Steam 的数据"就能并成一个任务。

## 9. 排查命令规范（诊断阶段给命令时遵守）

2026-11-05 所有者确认：**排查阶段可以直接给只读命令**（需求阶段仍以后台页面优先）。下面几条是这几次真实排查
踩出来的，照抄能少返工：

1. **只读优先**：`cat` / `ls` / `grep` / `ps` / `SELECT`；任何写操作（`DELETE`/`UPDATE`、重启、改配置）先征得同意。
2. **复杂脚本走 heredoc**，别在 `-e` 里拼转义：
   ```bash
   docker exec -i steamdeals sh -c 'cat > /tmp/x.mjs' <<'EOF'
   import { openStore } from '/app/src/store/index.js';
   const s = await openStore(process.env.DATABASE_URL, {});
   console.log((await s.query('select 1 as ok')).rows);
   await s.close();
   EOF
   docker exec steamdeals node /tmp/x.mjs
   docker exec steamdeals rm -f /tmp/x.mjs
   ```
3. **SQL 里不要写 `$$`**：PG 会当 dollar-quoted 字符串开头，报 `unterminated dollar-quoted string`；
   空串用 `''`，或改成 `length(col) = 0`。
4. **别假设表/列名**：`sync_runs` 的结束时间是 `finished_at`（写成 `ended_at` 直接 42703）。
5. **进程排查不要只 grep 一个任务名**：会漏掉真正在跑的那个（本项目漏过 `steam-prices`）；
   用 `/proc/*/cmdline` 或 `ps -eo pid,etime,args` 全量列。
6. **两处日志都看**：`docker logs`（stdout，子进程 `stdio: inherit` 也在这里）与 `logs/app-*.jsonl`（文件、受级别过滤）；
   事件名先确认（是 `scheduler.job_start`，不是 `job_started`）。
7. **"零日志"先怀疑观测开关**：nginx 可能是 `access_log off;`，应用侧有日志级别过滤。
8. **每条命令写清"看什么 + 怎么判读 + 预期值"**，不要丢一堆命令让人猜。
9. **按"最快定位"排序**：第一条就能区分大部分可能（例：先读 `data/scheduler-status.json` 判断调度器是否存活）。
