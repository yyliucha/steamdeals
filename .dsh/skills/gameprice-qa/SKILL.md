# 质检（SteamDeals / gameprice）

> **路径基准**：下文 `docs/…`、`src/…`、`frontend/…`、`test/…` 都相对**仓库根** `F:\dsh\gameprice`，
> 不是本 SKILL.md 所在目录。开场先 `git rev-parse --show-toplevel` 确认在仓库根。
>
> **技能文件位置**：`.dsh/skills/gameprice-qa/SKILL.md`，**自 2026-11-09 起随仓库提交、推 GitHub**；
> 本机 DSH 扫描路径 `F:\dsh\.dsh\skills\gameprice-qa` 是指向它的 junction（仅本机环境配置，不入库）。
> 别的机器 clone 后如需 DSH 发现该技能，按同样方式建 junction；**不要再维护第二份副本**。
>
> **分工**：`gameprice-requirements` 出需求与开发描述 → `gameprice-dev` 实现并验证 →
> **`gameprice-qa` 验收核对**。结论只有三档：✅ 放行 / ⚠️ 有条件放行 / ❌ 打回。

## 0. 边界：只判不改

| 做 | 不做 |
|---|---|
| 读需求、拆条目、列检查计划、git/代码取证 | 写业务代码、改需求文档、改测试、改文档 |
| 亲自重跑验证命令（§3 第 6 步） | `git add/commit/tag/push`、发版、触发构建 |
| 写 `docs/QA-<TOPIC>.md` + 对话给结论 | 碰服务器、连生产库（硬规则 4） |
| 打回复检（§8），多轮留痕 | 替开发"顺手修"任何东西 |

- QA 报告 `docs/QA-<TOPIC>.md` **默认不提交**（所有者要求存档时才提交）。
- 引用不重复：验证命令以 `gameprice-dev` §7 为准；"没跑过不许说做完"引用 `verify-before-done`。
- 若同会话质检出现放水（放行后仍有漏功能），改用**独立裁判**：新开会话，只传规格路径 + 基线/HEAD 哈希，
  不带开发会话的任何结论。

## 1. 触发与适用

- `gameprice-dev` 在「提交推 main」之后**必须**调用本技能；❌ 打回项补齐并复检通过，才算交付。
- **何时用**：开发完成后初检、打回复检后。
- **何时不用**：需求讨论阶段（那是 `gameprice-requirements` 的事，质检不参与方案取舍）。
- **输入来自待办清单（2026-11-06 所有者要求）**：开发者说"做完了"时必须给出 **TODO 编号**；
  质检按该编号在 [docs/TODO.md](../../../docs/TODO.md) 找到条目与规格，不接受"你去看我提交"这种转述。
- **检查完必须回写状态**：把该条目从 `待质检` 改成 `质检通过` 或 `质检打回`（打回时在条目里写一句打回摘要），
  并在 `docs/REQUIREMENTS-INDEX.md` 同步；**质检不写 `已发布`**（那是发版后的事）。回写状态后运行 `npm run todo:progress`
  （README「开发进度」块由 CI `docs-progress` 校验，规则见 [docs/TODO-PROGRESS.md](../../../docs/TODO-PROGRESS.md)）。
- **并发写 TODO（2026-11-06 所有者要求）**：回写状态前先探测占用（`git status --short` + `LastWriteTime`
  2 分钟内被改过 + `.git/index.lock`）；**发现被占用立即停手**——不改 TODO / INDEX、不提交，把"想改哪个编号、
  证据（mtime / 最近提交）、疑似占用方"报给所有者，**由人工决定**怎么处理；所有者确认可写后再重读两份文件全文、
  用 `edit` 定点替换。完整规则见 [docs/HANDOVER.md](../../../docs/HANDOVER.md) §10。

## 2. 输入：判据与证据，都不信转述

1. **判据**：docs 规格文档「验收」章节的编号清单 + 开发描述（requirements §6）的【范围】【验收】【红线】。
   判定以**规格验收为唯一判据**，开发描述只当背景。
2. **版本核对**：开工先 `git log --oneline -5 -- docs/` 确认规格没在开发期间被改；不一致先提示，
   以最新 HEAD 的规格为准。
3. **范围**：开发描述【范围】的"做/不做"（分批交付只判本期）；没有范围声明就默认规格全量。
4. **基线**：开发描述【背景】里的 HEAD 短哈希 = 基线；证据范围 `git diff <基线>..HEAD`。
5. **git 取证**（不信开发转述"我做了、全绿了"）：
   ```powershell
   cd F:\dsh\gameprice
   git status --short
   git log --oneline -5
   git diff --stat <基线>..HEAD
   git diff <基线>..HEAD
   git tag --list
   ```
6. **条目判定以最终仓库状态为准**：diff 只用来定位改动与"查多"；某条目由基线前已有代码满足也算 ✅
   （注明证据来源），不能因为"不是本次 diff 做的"就误判缺失。

## 3. 七步流程

0. **对序号**：确认开发者给的 TODO 编号存在、且状态是 `待质检`/`已实现待发版`；否则先要编号再开工。
   再看条目的 `依赖：`——前置还没到 `质检通过`/`已发布` 时判"暂缓检查"并说明，不要硬判 ❌。

1. **拆条目**：规格「验收」逐条 + 纪律项 → 可判定条目表（编号、要求、可观测点）。
2. **列检查计划**：每条写检查手段——grep 什么、读哪个文件、跑什么命令。先透明，后动手。
3. **双层核对**：规格 → 开发描述改动清单（清单本身漏了条目 = 开发漏）；再清单 → 代码。
4. **逐条取证**：
   - 每条到代码找证据，证据格式 `文件:行号 + 关键片段`；
   - **四方一致**：后端接口 / 前端消费 / 测试断言 / 文档描述，同一条目四处联动缺一即漏；
   - **测试"真锁住"**：打开测试文件看断言是否锁住该行为；"测试全绿" ≠ "测试覆盖了本条目"。
5. **查多**：diff 全量过目；需求外改动单列「风险提醒」，不直接判错。
6. **亲自重跑验证**（以 `gameprice-dev` §7 为准）：
   ```powershell
   cd F:\dsh\gameprice
   npm test                # 主链全绿
   npm run frontend:build  # diff 动过 frontend/ 必跑
   npm run scan            # 必跑
   ```
   纯文档/注释/文案改动可降级为抽查（grep 关键片段，并写明"本改动无自动化测试可跑"）。
   **验证失败 = 直接打回，质检不修。**
7. **出报告**：写 `docs/QA-<TOPIC>.md`（§5 格式，**必须含「功能清单」表**）+ 对话里给头部三行结论与同一张功能清单（§9 格式）。

## 4. 判定标准

| 判定 | 含义 |
|---|---|
| ✅ 通过 | 代码证据支持，功能行为满足需求 |
| ❌ 缺失 | 仓库里找不到实现（含"改动清单列了但代码没做"） |
| ⚠️ 偏差 | 有实现但行为不符（文案错、位置错、口径错、范围不符） |
| 🔎 需人工确认 | 本地/静态无法验证（页面目视、真实 Steam 数据、部署后效果） |
| 📋 需求缺陷 | 验收标准歧义/矛盾/不可验证 → 打回需求方，不算开发问题 |

- **行为满足即通过**，实现方式自由（提示用 el-alert 还是 `<p>` 都行）；只有行为不符才判 ⚠️，防机械假打回。
- **无法验证绝不硬判**：宁写 🔎 也不猜 ✅/❌——质检的信用靠这条，防质检自己假通过。

```

> 结论：✅ 放行 / ⚠️ 有条件放行 / ❌ 打回 —— 通过 X / 缺失 Y / 偏差 Z / 需人工确认 W

| # | 编号 | 功能（用户视角） | 入口（页面/按钮/接口） | 状态 | 证据（文件:行 / 命令） |

| 1 | AH | 彻底删除用户 | 后台 → 用户管理 → 删除 | ✅ | AdminExtras.vue:… |
| 2 | AH | 删除后列表立刻刷新 | 同上 | ✅ | … |

## 逐条核对（规格验收 → 证据）

| # | 条目（规格验收） | 检查手段 | 证据（文件:行） | 判定 |
|---|---|---|---|---|
| 1 | … | grep "…" | src/xx.js:42 | ✅ |
…

## 打回清单（按严重度排序，可执行：补什么、在哪补）
- 条目 N：缺什么 → 建议在哪补（文件/接口/测试/文档）

## 需人工确认
- 条目 M：为什么本地验不了，上线后看什么

## 争议项（待所有者裁定）
- 条目 K：开发申辩 … / 质检意见 …

## 复检记录
- 第 1 轮（日期）：打回 N 条 → 开发补齐（commit <哈希>）→ 第 2 轮：只重查打回项 + 新增 diff + npm test 兜底 → ✅ 放行
```

- **功能清单是必出项（2026-11-06 所有者要求）**：把本编号（或本批多个编号）交付的**所有用户能感知的功能**
  逐条列出来——不是抄规格验收条目，也不是列"改了哪些文件"；所有者靠这张表判断"这个功能到底有没有"。
- 一条功能一行：规格 §验收 的每条可观测能力都落到一行，**不许合并、不许抽样**；多编号时加编号列，全部列出。
- 状态四档：`✅ 已交付` / `⚠️ 偏差` / `❌ 缺失` / `🔎 待人工确认`，与「逐条核对」的判定一致。
- 「入口」写清用户从哪点进去（页面 → 按钮 / 接口路径），让所有者能自己复验。
- 表里每个 `⚠️`/`❌` 必须能在「打回清单」按编号找到对应项。
- 这张表要**同时出现在报告和对话汇报里**（§9）：报告存档，对话给所有者看。
- 头部三行结论，所有者 10 秒看懂。
- 打回清单严重度：漏验收 = 必修；偏差 = 必修或说明；风险 = 记录即可。
- QA 文档默认**不进 git**；相对链接必须指向真实文件（`test/docs.test.js` 会校验 docs 断链）。

## 6. 纪律固定检查项（每条都查，对应 gameprice-dev §0/§8 硬规则）

1. `git tag --list`：无擅自新增 tag（硬规则 5，打 tag = 触发构建）；
2. diff 是否碰部署/服务器配置（compose 文件、DEPLOY 相关、凭据）；
3. 构建产物（`frontend/dist/`、`*.log`、`data/*-pgdata/`、`out/`、`logs/`）是否进了提交；
4. 是否按要求推 `main`（开发描述【红线】要求）；
5. 文档收尾：`docs/PROJECT-OVERVIEW.md` 是否同步（gameprice-dev §6 必改项，"代码新、文档旧"即漏）。

## 7. 典型漏项清单（优先按此排查；发现新漏项模式就追加，skill 越用越准）

1. 后端删/改字段，前端没同步（接口返回体改了、调用方没跟上）
2. 测试没改，`npm test` 照样全绿——断言没锁住新行为
3. 文档未同步（PROJECT-OVERVIEW / README / CHANGELOG / 规格状态词）
4. 开发描述改动清单本身漏了规格条目（双层核对第一层）
5. 顺手改了需求外代码（scope creep）
6. Element Plus 新组件没注册 → 页面**静默**不渲染
7. 新测试没进 `package.json` 的 test 主链（主链跑不到 = 没测）
8. 日志事件没按 `域.动作`，失败路径没带原因
9. 状态词写错（把"待开发"写成"已发布"）
10. 验收里"真机/线上才可验证"的条目没标 🔎 直接判了 ✅

## 8. 复检（第 N 轮）

- 只重查：打回项 + 新增 diff + `npm test` 兜底（防"修 A 弄坏 B"）；不每次全量重来。
- 每轮在报告「复检记录」留痕，直到 ✅ 放行。
- 开发对判定不服 → 写进「争议项」（申辩 + 质检意见并列），质检不私了，所有者裁定。

## 10. 收尾自检（每次结束前逐条过）

1. 每条判定都有证据（文件:行 + 片段）？没有证据的判定不算数。
2. 🔎 项诚实列出了吗？有没有硬判 ✅/❌？
3. 重跑验证的命令与关键输出贴了吗？
4. 报告落 `docs/QA-*.md` 且未提交了吗？
5. 打回清单可执行吗（补什么、在哪补，开发照着能做）？
6. 双层核对两层都查了吗（清单漏条目也算开发漏）？
7. **TODO 状态回写了吗**：该编号现在是 `质检通过` 还是 `质检打回`？与报告结论一致吗？
8. **"已检查/未检查"两行写了吗**？没检查的必须写原因，不许沉默略过。
9. **功能清单表出了吗**：覆盖本批全部功能、一条功能一行、状态与打回清单一致、对话里也原样贴了？
