# 开发交接说明（唯一入口）

> 给**开发会话**（`gameprice-dev`）和**质检会话**（`gameprice-qa`）看。
> **不要问"这次做什么"——答案永远在 [TODO.md](TODO.md)。**
> 所有交互以待办清单为中心：来源是它、状态改在它、汇报按它的编号。

## 0. 一句话流程

```
读 docs/TODO.md → 挑状态为「待开发 / 开发中」的条目 → 按条目里的规格实现
→ 改 TODO 里该条目的状态 → 汇报「已做哪些编号 / 未做哪些编号及原因」
```

## 1. 唯一事实来源

| 东西 | 作用 |
|---|---|
| [TODO.md](TODO.md) | **唯一排期与状态来源**。章节字母 = 批次编号（S/T/U/V/W/X/Y/Z/AA/AB/AC/AD…） |
| [REQUIREMENTS-INDEX.md](REQUIREMENTS-INDEX.md) | 总账：每个编号对应哪份规格、当前状态、有没有开发描述 |
| 条目里链着的 `docs/*.md` | 该批的规格（改什么、为什么、验收几条） |

**每条待办必须有一行 `**状态：…**`**，状态词只有这几个：

`待开发` / `开发中` / `已实现待发版` / `待质检` / `质检通过` / `质检打回` / `已发布 vX.Y.Z` / `待排查` / `待决策` / `已过时`

## 2. 开工流程（每次会话照做）

1. **读**：`docs/TODO.md` 全文（至少读完"待开发/待排查/待决策"三类），再读所选条目的规格；
2. **选**：只做状态为 `待开发` 或 `开发中` 的条目；一次可以选多条，但**按顺序做，做一条更新一条**；
3. **停**：
   - `待决策` 的**不要动**，把缺的决策列出来交给所有者；
   - `待排查` 的只做只读定位，不猜测着改代码；
   - `已过时` 的不要碰；
4. **做**：按规格实现，测试用例与文档同步（`gameprice-dev` §6）；
5. **收尾**：
   - 改 TODO：该条目 `**状态：已实现待发版**`，补提交哈希；
   - 改规格文档头部的状态行；
   - README 不再有「开发进度」生成块（2026-11-12 下线），改状态只需改本文件 + INDEX；
   - 同步 `PROJECT-OVERVIEW.md` / `CHANGELOG.md` / `DELIVERY.md`（按规格要求）；
   - 调 `gameprice-qa` 质检；打回就修，直到 `质检通过`；
6. **发版**：只有收到所有者的「构建 vX.Y.Z」指令才打 tag；发版后把 TODO 状态改成 `已发布 vX.Y.Z`。

## 3. 汇报格式（对话里必须给，缺一段都算没汇报）

```
✅ 已做：<编号> <一句话> —— 验证：<命令> → <关键输出>
⏳ 未做：<编号> —— 原因：<等决策 / 等日志 / 依赖 XX / 本轮没排到>
📄 状态更新：docs/TODO.md 里改了 <哪几条的状态>，现在分别是 <新状态>
🧪 质检：第 N 轮 → <结论>（报告 docs/QA-*.md）
🔖 提交：<短哈希>
```

**"未做"必须写，哪怕原因是"没排到"**——所有者靠这两行知道清单的真实进度。

## 5. 红线（与 `gameprice-dev` §8、硬规则 4/5 一致）

- **不自行打 tag、不触发构建**——等"构建 vX.Y.Z"；
- **不碰服务器**（除规格里明确要求、且所有者同意的只读排查命令）；
- **没跑过的验证不许说"做完了"**；
- **没做的条目不许偷偷改状态**；改状态必须与汇报、与真实验证一致。

## 6. 状态维护纪律（最容易被破坏的一条）

| 情况 | 正确状态 |
|---|---|
| 代码写完、本地验证通过、还没发版 | `已实现待发版` |
| 已交给质检、还没出结论 | `待质检` |
| 质检通过 | `质检通过` |
| 质检打回 | `质检打回`（并在条目里写打回项摘要） |
| 已打 tag 且 CI 双绿 | `已发布 vX.Y.Z` |
| 只做了定位、没改代码 | 保持 `待排查`，把结论写进条目 |
| 等所有者回答才能继续 | `待决策`，问题写进条目 |

质检会话（`gameprice-qa`）只负责 `待质检 → 质检通过 / 质检打回`，**不写"已发布"**。

**改状态只改两处**（2026-11-12 简化）：`docs/TODO.md` 的状态行 + `docs/REQUIREMENTS-INDEX.md` 对应行。
README 不再有「开发进度」生成块、也没有 `docs-progress` 门禁（2026-11-12 所有者决定下线：它依赖容易漏掉的手工步骤，
反复变红且不参与构建；详见 [TODO-PROGRESS.md](TODO-PROGRESS.md) §0）。

## 7. 新需求进来时，给开发会话只发这一句

需求会话把新需求落进 TODO 之后，**不要**再把规格内容复制一遍发过去（两处内容会漂移）。
直接发下面这段，把 `<编号>` 换掉即可：

```
新需求已入待办：docs/TODO.md 的 <编号>（状态：待开发）。
先读 docs/HANDOVER.md（流程与状态词）→ docs/TODO.md 该条目 → 条目里链的规格文档。
做完把该条目状态改成「已实现待发版」，调 gameprice-qa 质检，然后按 HANDOVER §3 汇报
「已做 / 未做 / 状态更新」三行。
```

一次多个需求的写法：

```
按 docs/TODO.md 处理状态为「待开发」的条目，顺序：<编号1> → <编号2> → …；
每条做完立刻改状态，不要攒到最后一起改。
```

**批次策略（默认）**：一次只发 **1 个编号**；最多 2 个（必须给顺序）。原因：每批的规格、验收命令、
质检范围都不同，一个会话里塞太多会让"做完"和"没做"混在一起，质检也判不清。
大条目（如 AC 有 11 项）应按子项拆开发，不要一次全做。

**不要这样发**：把规格正文、验收清单、代码落点整段贴在消息里——TODO 与规格里已经有了，
重复一遍只会造成"消息里改了、文档没改"的分叉。
## 8. 端到端时间线（谁做什么）

| 步 | 谁 | 动作 | TODO 状态 |
|---|---|---|---|
| 1 | 需求会话 | 写规格、建条目、给编号 | `待开发` |
| 2 | 开发会话 | 认领、实现、跑验证、同步文档 | `开发中` → `已实现待发版` → `待质检` |
| 3 | 质检会话 | 按编号核对、重跑验证 | `待质检` → `质检通过` / `质检打回` |
| 4 | **所有者** | 说一句"构建 vX.Y.Z" | 不变 |
| 5 | 开发会话 | 打 tag、等 CI 双绿 | `已发布 vX.Y.Z` |
| 6 | 部署人员 | 按 DEPLOY 升级容器 | 不变 |
| 7 | **所有者** | 把下一个编号发给开发会话 | 下一条从 `待开发` 开始 |

**不需要每做一条都回来找需求会话要编号**——编号已经在 TODO 里，所有者直接发给开发会话即可。

只有三种情况需要回到需求会话：

1. **有新需求**（要写规格、建条目）；
2. **条目卡在 `待决策`**（需要所有者拍板，我负责问清楚并改状态）；
3. **条目卡在 `待排查`**（需要只读诊断，出了结论才转 `待开发`）。

**可以攒批发版**：多条都到了 `质检通过`，可以一次构建一个版本（例：AB + AD 合成 v1.17.0），
不是每条都必须单独发版——只要它们各自通过了质检，且 CHANGELOG 写清包含哪几条。
## 9. 依赖与解锁（一条做完才能定位下一条）

真实场景：**编号 1 先加日志/先修管道，编号 2 才有数据可定位**。这类关系必须写进 TODO，不靠口头提醒。

### 9.1 写法（需求会话负责）

每个条目在 `**状态：**` 下面补两行：

```
**依赖：** AB（无则写"无"）
**解锁：** AA（本条完成后谁可以开工；无则写"无"）
```

有前置且前置未完成时，状态写 **`依赖阻塞`**（而不是 `待开发`），开发不会认领。

### 9.2 解锁动作（开发会话负责）

完成一条后，**必须检查 TODO 里哪些条目的 `依赖：` 指向它**，把那些条目从 `依赖阻塞` 改成 `待开发`，
并在汇报里单独给一行：

```
🔓 解锁：AA、AC6（前置 AB 已完成，现在可以开工）
```

没有依赖关系的也写 `🔓 解锁：无`——**不许省略这一行**，所有者靠它决定下一条发什么。

### 9.3 质检动作（质检会话负责）

开查前先看条目的 `依赖：`：前置没到 `质检通过`/`已发布`，直接判"暂缓检查"并说明，不要硬判 ❌。

## 10. TODO 被其他会话占用时怎么办（2026-11-09 所有者新规）

开发 / 需求 / 质检三个会话可能同时改 `docs/TODO.md` 与 `docs/REQUIREMENTS-INDEX.md`。
**规则：被占用就跳过 TODO/INDEX 的写入，照常干活；任务状态统一留到「收尾复盘」由本批最后提交的会话补齐。**

### 10.1 写前探测（改这两份文件前必做，命中任一即视为"被占用"）

```powershell
cd F:\dsh\gameprice
git status --short docs/TODO.md docs/REQUIREMENTS-INDEX.md
(Get-Item docs/TODO.md).LastWriteTime      # 2 分钟内被改过 = 可能有人正在写（自己刚写过的除外）
Test-Path .git/index.lock                  # True = 有 git 操作在跑
```

### 10.2 发现占用：跳过 TODO/INDEX，照常干活

- **不写** `docs/TODO.md`、`docs/REQUIREMENTS-INDEX.md`：不改状态、不加条目、不改 INDEX 行、不 `git add` 这两份文件；
- 不回滚、不 `git stash`、不覆盖、不提交这两份文件；
- **照常做其余全部工作**：改代码、补测试、跑验证、写规格 / QA 报告、提交推 main（提交只 `git add` 自己的文件，绝不 `git add -A`）；
- 把「待回写 / 待建的状态与条目」记进提交信息、汇报与收尾清单（§10.3），**不要只留在对话里**。

### 10.3 收尾复盘（本批最后提交的会话负责，必须做）

1. 等对方提交（`git pull --rebase`）或确认对方已停笔；
2. **重读两份文件全文**，吸收别人的新增——"没读到就改"必然冲掉内容；
3. 用 `edit` **定点替换**补上本批状态 / 条目 / INDEX 行；**禁止整文件 `write` 覆盖**；
4. 核对全量状态：本批条目状态、`依赖：` / `解锁：` 联动、INDEX 行；
   发现别人的内容被冲掉 → 停手、保留现场上报所有者，不自行"补回"。

### 10.4 已经撞车（覆盖已发生）

- 立即停手，**保留现场**：不 commit、不 checkout、不 stash；
- 把 `git diff` 输出、被覆盖的条目编号与时间点报给所有者；
- 由所有者决定用 `git show HEAD:docs/TODO.md` / 备份 / 对方会话恢复；恢复动作本身也要先拿到指令。
