# 开发交接说明（唯一入口）

> 给**开发会话**（`steamdeals-dev`）和**质检会话**（`steamdeals-qa`）看。
> **不要问"这次做什么"——答案永远在 [TODO.md](TODO.md)。**
> 所有交互以待办清单为中心：来源是它、状态改在它、汇报按它的编号。

## 0. 一句话流程

```
读 docs/TODO.md（待办）→ 挑状态为「待开发 / 开发中」的条目 → 按条目里的规格实现
→ 改 TODO 里该条目的状态 → 汇报「已做哪些编号 / 未做哪些编号及原因」
→ 发布后条目整段移入 docs/DONE.md（已完成清单）
```

## 1. 唯一事实来源

| 东西 | 作用 |
|---|---|
| [TODO.md](TODO.md) | **唯一排期与状态来源（待办侧）**。只放未完成条目（`待开发`…`质检通过`）；章节字母 = 批次编号 |
| [DONE.md](DONE.md) | **已完成清单**（2026-11-18 起）：`已发布 vX.Y.Z` 与 `已过时` 的条目整段移入，只读追溯 |
| [REQUIREMENTS-INDEX.md](REQUIREMENTS-INDEX.md) | 总账：每个编号对应哪份规格、当前状态、有没有开发描述（含全部历史批次） |
| 条目里链着的 `docs/*.md` | 该批的规格（改什么、为什么、验收几条） |

**每条待办必须有一行 `**状态：…**`**，TODO 里只出现未完成态：

`待开发` / `依赖阻塞` / `开发中` / `已实现待发版` / `待质检` / `质检通过` / `质检打回` / `待排查` / `待决策`

终态 `已发布 vX.Y.Z` / `已过时` 在发布/判定后**整段移入 [DONE.md](DONE.md)**（发布由 `steamdeals-build` 移动，过时由需求会话移动），不再留在 TODO。

## 2. 开工流程（每次会话照做）

1. **读**：`docs/TODO.md` 全文（至少读完"待开发/待排查/待决策"三类），再读所选条目的规格；
2. **选**：只做状态为 `待开发` 或 `开发中` 的条目；一次可以选多条，但**按顺序做，做一条更新一条**；
3. **停**：
   - `待决策` 的**不要动**，把缺的决策列出来交给所有者；
   - `待排查` 的只做只读定位，不猜测着改代码；
   - `已过时` 的不要碰；
4. **做**：按规格实现，测试用例与文档同步（`steamdeals-dev` §6）；
5. **收尾**：
   - 改 TODO：该条目 `**状态：已实现待发版**`，补提交哈希；
   - 改规格文档头部的状态行；
   - README 不再有「开发进度」生成块（2026-11-12 下线），改状态只需改本文件 + INDEX；
   - 同步 `PROJECT-OVERVIEW.md` / `CHANGELOG.md` / `DELIVERY.md`（按规格要求）；
   - 调 `steamdeals-qa` 质检；打回就修，直到 `质检通过`；
6. **发版**：**2026-11-27 起，批次条目 `质检通过` 后由开发/监工会话直接构建**（不必等所有者「构建」；所有者可随时叫停）——加载 `steamdeals-build` 按其 §0 触发规则执行；发版后把本批条目从 TODO **整段移入 [DONE.md](DONE.md)**（保留原文，状态行写 `已发布 vX.Y.Z`），并同步 INDEX 行。

## 3. 汇报格式（对话里必须给，缺一段都算没汇报）

```
✅ 已做：<编号> <一句话> —— 验证：<命令> → <关键输出>
⏳ 未做：<编号> —— 原因：<等决策 / 等日志 / 依赖 XX / 本轮没排到>
📄 状态更新：docs/TODO.md 里改了 <哪几条的状态>，现在分别是 <新状态>
🧪 质检：第 N 轮 → <结论>（报告 docs/QA-*.md）
🔖 提交：<短哈希>
```

**"未做"必须写，哪怕原因是"没排到"**——所有者靠这两行知道清单的真实进度。

## 6. 状态维护纪律（最容易被破坏的一条）

| 情况 | 正确状态 |
|---|---|
| 代码写完、本地验证通过、还没发版 | `已实现待发版` |
| 已交给质检、还没出结论 | `待质检` |
| 质检通过 | `质检通过` |
| 质检打回 | `质检打回`（并在条目里写打回项摘要） |
| 已打 tag 且 CI 双绿 | `已发布 vX.Y.Z` |
| 只做了定位、没改代码 | 保持 `待排查`，把结论写进条目 |
| 等所有者回答才能继续 | `待决策`，问题写进条目 |

质检会话（`steamdeals-qa`）只负责 `待质检 → 质检通过 / 质检打回`，**不写"已发布"**。

**改状态只改两处**（2026-11-12 简化）：`docs/TODO.md` 的状态行 + `docs/REQUIREMENTS-INDEX.md` 对应行。
README 不再有「开发进度」生成块、也没有 `docs-progress` 门禁（2026-11-12 所有者决定下线：它依赖容易漏掉的手工步骤，

## 7. 开发会话交接规范（2026-11-18 所有者新规：一需求一会话、全新无上下文）

**规则**：以后**一个开发需求一个会话**，开发会话是**全新会话、没有历史上下文**。所以交接消息必须**自包含**——
不依赖"前面聊过什么"，但**也不要把规格正文整段抄一遍**（会漂移）；正确做法是"**给足坐标 + 指路到权威文档**"。

**交接消息必须包含这 8 项**（缺一项就可能跑偏）：

| # | 内容 |
|---|---|
| 1 | **仓库与基线**：`F:\dsh\gameprice`（站点）/ `F:\dsh\steamdeals-app`（App）；当前 HEAD 与版本号；先 `git pull` |
| 2 | **技能**：先加载 `steamdeals-dev`（流程/红线/提交规范），完工调 `steamdeals-qa` |
| 3 | **编号**：`docs/TODO.md` 的哪个条目（状态「待开发」） |
| 4 | **规格**：条目里链的规格文档路径（开发会话自己读，不要贴正文） |
| 5 | **一句话范围**：做什么、不做什么（界外事项列 1–2 条） |
| 6 | **验收要点**：引用规格 §验收 / demo 断言表的位置 + 必须跑的测试命令 |
| 7 | **纪律**：开工改「开发中」、完工改「已实现待发版」；不自行打 tag、不碰服务器/生产库；只提交自己的文件 |
| 8 | **汇报格式**：按 HANDOVER §3 三行（已做/未做/状态更新） |

**标准模板**（复制后替换 `<…>`）：

```
【任务】SteamDeals 开发：<编号> <条目名>
【仓库】F:\dsh\gameprice（HEAD <sha>，版本 <x.y.z>）；先 git pull
【技能】先加载 steamdeals-dev；完工调用 steamdeals-qa
【条目】docs/TODO.md 的 <编号>（现状态：待开发）
【规格】<规格文件路径>（自己读；验收以规格 §验收 为准）
【范围】<一句话>；不做：<界外 1-2 条>
【验收】<规格 §验收 编号>；必须真跑 <相关测试> + npm run frontend:build + npm run scan，贴输出
【纪律】开工把条目改「开发中」，完工改「已实现待发版」；不自行打 tag、不碰服务器/生产数据；只提交本条目相关文件
【汇报】按 HANDOVER §3 给「已做 / 未做 / 状态更新」三行
```

**不要这样发**：
- ❌ 只发"做 <编号>"却不给仓库/规格路径（新会话找不到上下文）；
- ❌ 把规格正文、验收清单整段贴进消息（文档改了消息没改 → 两处分叉）；
- ❌ 一次塞多个编号（除非同批次且给顺序；默认一次 1 个）。

## 9. 依赖与解锁（一条做完才能定位下一条）

真实场景：**编号 1 先加日志/先修管道，编号 2 才有数据可定位**。这类关系必须写进 TODO，不靠口头提醒。

### 9.1 写法（需求会话负责）

每个条目在 `**状态：**` 下面补两行：

```
**依赖：** AB（无则写"无"）
**解锁：** AA（本条完成后谁可以开工；无则写"无"）
```

有前置且前置未完成时，状态写 **`依赖阻塞`**（而不是 `待开发`），开发不会认领。

### 9.2 解锁动作（开发会话负责）

完成一条后，**必须检查 TODO 里哪些条目的 `依赖：` 指向它**，把那些条目从 `依赖阻塞` 改成 `待开发`，
并在汇报里单独给一行：

```
🔓 解锁：AA、AC6（前置 AB 已完成，现在可以开工）
```

没有依赖关系的也写 `🔓 解锁：无`——**不许省略这一行**，所有者靠它决定下一条发什么。

### 9.3 质检动作（质检会话负责）

开查前先看条目的 `依赖：`：前置没到 `质检通过`/`已发布`，直接判"暂缓检查"并说明，不要硬判 ❌。

## 10. TODO 被其他会话占用时怎么办（2026-11-09 所有者新规）

开发 / 需求 / 质检 / 构建会话可能同时改 `docs/TODO.md`、`docs/REQUIREMENTS-INDEX.md` 与 `docs/DONE.md`（发布移入时）。
**规则：被占用就跳过 TODO/INDEX/DONE 的写入，照常干活；任务状态统一留到「收尾复盘」由本批最后提交的会话补齐。**

### 10.1 写前探测（改这三份文件前必做，命中任一即视为"被占用"）

```powershell
cd F:\dsh\gameprice
git status --short docs/TODO.md docs/REQUIREMENTS-INDEX.md docs/DONE.md
(Get-Item docs/TODO.md).LastWriteTime      # 2 分钟内被改过 = 可能有人正在写（自己刚写过的除外）
Test-Path .git/index.lock                  # True = 有 git 操作在跑
Test-Path docs/.ledger-lock                # True = 有会话正持有清单锁（视为被占用）
```

**清单锁**（2026-11-19 起）：写 TODO/INDEX/DONE/DELIVERY/ACTIVE-SESSIONS 前先
`node scripts/commit-own.mjs lock <编号>`，写完立即 `unlock <编号>`（锁文件已被 .gitignore 忽略，不入库；
写入工具见 `scripts/commit-own.mjs`）。清单改动提交同样走会话隔离脚本：
`node scripts/commit-own.mjs <编号> "<信息>" -- docs/TODO.md docs/REQUIREMENTS-INDEX.md`。

### 10.2 发现占用：跳过 TODO/INDEX/DONE，照常干活

- **不写** `docs/TODO.md`、`docs/REQUIREMENTS-INDEX.md`、`docs/DONE.md`：不改状态、不加条目、不改 INDEX 行、不移入 DONE、不 `git add` 这三份文件；
- 不回滚、不 `git stash`、不覆盖、不提交这三份文件；
- **照常做其余全部工作**：改代码、补测试、跑验证、写规格 / QA 报告、提交推 main（提交只 `git add` 自己的文件，绝不 `git add -A`）；
- 把「待回写 / 待建的状态与条目」记进提交信息、汇报与收尾清单（§10.3），**不要只留在对话里**。

### 10.3 收尾复盘（本批最后提交的会话负责，必须做）

1. 等对方提交（`git pull --rebase`）或确认对方已停笔；
2. **重读三份文件全文**，吸收别人的新增——"没读到就改"必然冲掉内容；
3. 用 `edit` **定点替换**补上本批状态 / 条目 / INDEX 行；**禁止整文件 `write` 覆盖**；
4. 核对全量状态：本批条目状态、`依赖：` / `解锁：` 联动、INDEX 行；
   发现别人的内容被冲掉 → 停手、保留现场上报所有者，不自行"补回"。

### 10.4 已经撞车（覆盖已发生）

- 立即停手，**保留现场**：不 commit、不 checkout、不 stash；
- 把 `git diff` 输出、被覆盖的条目编号与时间点报给所有者；
- 由所有者决定用 `git show HEAD:docs/TODO.md` / 备份 / 对方会话恢复；恢复动作本身也要先拿到指令。

### 10.5 不重复劳动（2026-11-18 所有者新规）

同一个编号 / 同一次验证，**不要两个会话同时做**。动手前先确认是否已有会话在进行中——命中任一即视为"他人进行中"：

| 依据 | 怎么查 |
|---|---|
| TODO 状态 | 该编号已是 `开发中`（开发）/ `待质检 / 质检通过 / 质检打回`（质检） |
| 报告或产物 | `docs/QA-<编号>.md` 已存在且刚被修改/已提交；或对应规格/实现已被提交 |
| 工作区 | `git status --short` 里已有该条目的未提交改动 |
| 对话声明 | 已有会话说"本次做 <编号>" |

**认定他人进行中 → 跳过并等待**：不重复实现、不重复跑验证、不重写报告；只做只读确认（看状态/看报告），
汇报里写清「跳过 <编号>：已由其他会话进行（依据 X），等待其结果」。发现两个会话已在做同一件事时，
**后启动方主动退出**，避免两边同时写同一批文件。

### 10.6 并发资源协调：活跃会话登记表（2026-11-19 起）

并行会话的四类冲突（同文件抢占、暂存区串扰、回退重放、独占资源）统一用
`docs/ACTIVE-SESSIONS.md` 登记表协调：
