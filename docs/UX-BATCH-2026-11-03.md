## 1. 愿望单归属 + 移除选择账号

### 现状

- 本站愿望单：`user_wishlist(user_id, game_id, steam_ids)`（`steam_ids` 是添加时选择的推送账号）。
- Steam 实际愿望单：`steam_wishlist(steam_id, appid)`。
- 列表/详情只返回布尔 `wishlisted`（[pg.js `WISHLISTED_SQL`](../src/store/pg.js)），**不返回归属**。
- 移除（[server.js](../src/server.js) `DELETE /api/wishlist/:appid`）一把全删：删本站行 + 回推所有含它的账号，用户不能选。
- 卡片徽标只显示「愿望单」三字（[Home.vue](../frontend/src/pages/Home.vue)）。

### 已确认

- 列表 + 详情都显示**账号名**；>2 个显示 `+N`（与「已拥有 · FF、XX」一致）。
- 移除弹窗列出「本站」+ 所有含该游戏的账号，**默认全选**，可取消勾选。

### 后端改动

1. 新增 `WISHLISTED_BY_SQL(uid)`（仿 `OWNED_BY_SQL`）：

```sql
(select coalesce(json_agg(json_build_object('steamId', sa.steam_id,
        'name', coalesce(sa.alias, sa.persona_name, sa.steam_id)) order by sa.steam_id), '[]'::json)
   from steam_wishlist sw join steam_accounts sa on sa.steam_id = sw.steam_id
  where sa.user_id = $uid and sw.appid = g.steam_appid)
```

2. 列表（`searchGames` compact/详细两处）与 `gameDetail` 增加：
   - `wishlisted_by`：上面聚合的数组；
   - `site_wishlisted`：`exists(select 1 from user_wishlist uw where uw.user_id=$uid and uw.game_id=g.id)`。
3. `DELETE /api/wishlist/:appid`（及 `/id/:id`）改为接受 JSON body：

```json
{ "steamIds": ["7656...", "..."], "siteWishlist": true }
```

- `siteWishlist=true` → 删 `user_wishlist` 行并清理 `source='user_wishlist'` 的自动提醒（现有逻辑）；
- `steamIds` 里勾选的账号 → 逐个 `pushWishlist({action:'remove'})`，成功才删 `steam_wishlist` 行（失败保留并返回 failed）；
- **兼容**：body 缺省时保持旧行为（删本站 + 回推全部含它的账号）。
4. `POST /api/wishlist` 返回增加 `alreadyIn: [steamId]`（这些账号本来就含有该游戏，未重复推送）。

### 前端改动（Home.vue）

- 徽标：`愿望单` 后追加账号名（`wishlistByText(game)`，与 `ownedByText` 同款逻辑）。
- 详情弹窗：新增一行「愿望单账号：本站 / FF、Happy」，悬停显示 SteamID。
- 添加弹窗（`wishlistPick`）：账号列表标注「已在愿望单」（来自 `wishlisted_by`），默认不勾选已存在的。
- 新增移除弹窗（`wishlistRemovePick`）：复选框「本站愿望单」+ 每个账号（默认全选）；确认后调 DELETE 传 `{steamIds, siteWishlist}`。

### 验收

1. 两个账号都含该游戏 → 卡片显示「愿望单 · FF、Happy」，详情列全。
2. 移除时取消勾选某账号 → 该账号收到 Steam 移除、`steam_wishlist` 行删除，其余账号与本站不受影响。
3. 只取消勾选「本站」→ `user_wishlist` 保留，Steam 侧照常移除。
4. 旧调用（无 body）行为不变。
5. `npm test` 全绿（新增 `steam-accounts`/API 断言）；`npm run frontend:build` 通过。

## 2. 自动封禁与「异常审核」联动

### 现状与根因（已定位）

- 自动封禁写 `ip_abuse.banned_until`（[ratelimit.js `applyBan`](../src/ratelimit.js)）。
- 「异常审核」列表 [pg.js `listAbuseReviews`](../src/store/pg.js) 只按 `status='pending'` 查，**不检查 IP 是否已封**。
- 结果：被封 IP（如 34.70.39.109）仍留在待审列表。

### 已确认

- **仅过滤显示**：封禁期内的 IP 不出现；解封后自动恢复（保留原始审核数据，不写状态）。

### 后端改动

1. `listAbuseReviews` 增加条件：

```sql
and not exists (select 1 from ip_abuse a where a.ip = r.ip and a.banned_until is not null and a.banned_until > now())
```

2. `countPendingReviews` 同样排除被封 IP（否则"待审 N 条"与列表不一致）。

### 前端

- 无需改动；建议在审核页加一句提示：「已自动封禁的 IP 不在待审列表，可在『封禁与白名单』查看」。

### 验收

1. 构造：`abuse_reviews` 有一条 pending，且 `ip_abuse.banned_until > now()` → 审核列表与计数都不含它。
2. 把 `banned_until` 置空（解封）→ 该记录恢复显示。
3. PGlite 单测覆盖两种状态；`npm test` 全绿。

## 3. 站点通知中心

### 现状与根因（已定位）

- 后端 `/api/announcements` 正常（active + 时间窗）。
- 前端只在进入首页时弹一次未读弹窗，已读 id 存 `localStorage['steamdeals.notice-read.v1']`；
  点「我知道了」后**没有任何再次查看入口** → 用户"再也看不到"。

### 已确认

- 顶栏加**铃铛 + 未读角标**，点开**抽屉**显示全部有效公告（已读/未读区分）；
- 未读弹窗保留（进站有未读时仍弹一次）。

### 后端改动

1. 新表（幂等建表，放 `ensureSteamSchema` 同级的 schema 初始化处）：

```sql
create table if not exists announcement_reads (
  user_id bigint not null references users(id) on delete cascade,
  announcement_id bigint not null references announcements(id) on delete cascade,
  read_at timestamptz not null default now(),
  primary key (user_id, announcement_id)
);
```

2. `GET /api/announcements`：登录用户附带 `readIds: number[]`（该用户已读的公告 id）。
3. 新增 `POST /api/announcements/read`：body `{ ids: number[] }`（登录用户写表；游客只存本地，不调用）。
4. 管理员侧不变。

### 前端改动（Home.vue）

- 顶栏铃铛组件：未读数 = 有效公告中未读的条数；点击开 `el-drawer`。
- 抽屉：公告列表（未读高亮 + 已读淡色），「全部标为已读」按钮；每条显示级别/标题/正文/时间。
- 已读逻辑：登录用户调 `POST /api/announcements/read`；游客写 localStorage（保留现有 key，改成 id 数组）。
- 未读弹窗：仍显示未读公告；「我知道了」= 全部标读。

### 验收

1. 发布新公告 → 铃铛出现未读角标；抽屉里未读高亮。
2. 标读后角标消失；刷新/换页仍能看到（抽屉里已读态）。
3. 登录用户换浏览器 → 已读状态跟随账号（服务端存储）。
4. 游客：本地记录生效，换浏览器提示会有未读（可接受，文档注明）。
5. 单测：read 接口 + 聚合；`npm test` 全绿。

## 4. 移动端响应式

### 现状与根因

- `index.html` 已有 viewport meta；CSS 断点 1200→3 列、760→2 列、420→1 列；`Home.vue` 有 `isNarrow`（≤640）。
- 截图显示**3 列 + 小字**，等于渲染宽度约 980px：手机浏览器开了「桌面版网站」或内嵌 WebView 忽略 viewport。
- 因此**不能只靠 CSS 断点**，需要一个"强制移动布局"的兜底。

### 已确认

- 响应式重做（一套组件），**不做**第二套页面。

### 实现方案

1. **兜底判定**（关键）：前端检测

```js
const forceMobile = matchMedia('(max-width: 640px)').matches
  || (screen.width <= 640 && innerWidth > 700); // 桌面版模式特征
```

命中时给 `document.documentElement` 加 `mobile-layout` 类，CSS 用 `.mobile-layout` 覆盖断点（不依赖 viewport 是否正确）。

2. **断点设计**（前台）：
   - `>1024`：4 列（现状）；
   - `≤1024`：3 列；
   - `≤768`：2 列紧凑卡；
   - `≤480` 或 `.mobile-layout`：**单列**卡片，字号 ≥13px，按钮高度 ≥40px。
3. **移动端布局**（`.mobile-layout` / ≤640）：
   - 顶栏：只留品牌 + 铃铛 + 菜单（主题切换/登录收进菜单）；
   - 筛选：工具栏收进「筛选」抽屉（搜索框留在顶部）；
   - 卡片：封面 + 标题 + 价格 + 两行按钮（感兴趣/不感兴趣；已拥有/愿望单收进详情）；
   - 详情：全屏 dialog（100vw/100vh），关闭按钮固定；
   - 分页：改为「加载更多」或紧凑分页（保留每页 20）；
   - 触摸目标 ≥44px；字号正文 ≥13px；行高 1.6。
4. **不引入新依赖**；只用 CSS + 已有 `matchMedia`。

### 验收

1. 手机（系统浏览器）打开：单列卡片、字号可读、无横向滚动。
2. 即使浏览器开了「桌面版网站」（模拟：`screen.width<=640` 且 `innerWidth` 900+），也进入移动布局。
3. PC 1280/1440 宽：显示与现状一致（无回归）。
4. `npm run frontend:build` 通过；在 Chrome DevTools 设备模拟（iPhone 12/SE、Pixel）逐屏截图核对。
